DIVIDEND OS 장기운영 QA 설계·실행 기준 FINAL v3
작성일: 2026-09-28 (KST)
개정 방향: 개인용 앱 / 최초 구축부터 30~35년 운영 전제
최종 적용 원칙: 핵심 안전성은 완성형으로 구축하고 기업용 과잉 QA는 제외
권장 저장 위치: DividendOS 저장소의 docs/QA_POLICY.txt

======================================================================
1. 문서 목적
======================================================================

이 문서는 DividendOS를 수정할 때 어떤 QA를 어느 강도로 실행해야 하는지 정한다.
목표는 기능 추가 때마다 사용자가 모든 화면을 처음부터 수동 검사하지 않아도 되게 만드는 것이다.

이 앱은 개인 1인이 장기간 사용하는 금융 앱이다.
기업용 운영조직은 필요 없지만 다음 영역은 엄격히 검증한다.

- 매수·매도·배당·수수료·세금 계산
- 실제·확정·예상 배당 구분
- ROC·원금·총수익
- 환율과 통화
- 토스 읽기 연동과 중복 방지
- 기업행위와 장기 데이터 보존
- 백업·복원·클라우드 충돌
- 모바일 화면·PWA·보안

QA의 기본 원칙:
- Node 24 + TypeScript 7 strict 통과만으로 완료 처리하지 않는다.
- 새 핵심 기능에는 단위·통합 또는 E2E 테스트를 함께 추가한다.
- 실제 라이브 빌드에 들어가는 소스를 테스트한다.
- 운영 사용자 데이터와 QA 데이터를 완전히 분리한다.
- 토스 시크릿·토큰·계좌정보를 fixture·로그·영상에 넣지 않는다.
- QA 종료 후 테스트 거래·배당·종목·계정 연결 데이터는 0건이어야 한다.
- 재시도로 우연히 통과한 테스트를 정상 PASS로 숨기지 않는다.
- 작은 변경에는 타깃 QA, 고위험 변경과 큰 배포에는 전체 QA를 실행한다.

======================================================================
1-A. 처음부터 구축할 장기 QA 기반
======================================================================

장기 QA는 DividendOS 완성 뒤 붙이는 별도 작업이 아니다.
전체 TypeScript 전환, 금융 도메인 분리, 저장 구조 정리 단계부터 같이 구축한다.
처음부터 수천 건을 수동 입력하지 않고, 검산된 작은 기준 데이터와 재현 가능한
장기 생성기를 만들어 기능이 늘어도 QA 유지비가 폭증하지 않게 한다.

[논리적 분류 — 전부 별도 파일·폴더로 만들 필요는 없음]

tests/
- unit/                    금융 계산·중복 판정·검증 함수
- integration/             저장소·마이그레이션·토스 서버 경계
- e2e/                     Playwright 사용자 흐름
- fixtures/golden/         독립 검산한 불변 계산 사례
- fixtures/legacy/         과거 schema·백업 포맷
- fixtures/api/toss/       비식별 토스 성공·오류·정정 응답
- fixtures/corporate/      분할·병합·합병·청산 이벤트
- fixtures/bugs/           실제 발견 버그 최소 재현 자료
- factories/               종목·거래·배당·목표 기본 생성기
- generators/              1·5·10·30년 seed 기반 생성기
- visual/                  기준 화면과 승인 기록

초기에는 관련 항목을 한 파일에 묶어도 된다. 파일이 지나치게 길어지거나 변경 이유가
달라질 때만 분리한다. 테스트만을 위해 수십 개의 빈 폴더·빈 파일을 만들지 않는다.
실제 폴더명은 저장소 구조에 맞춰도 되지만 역할과 데이터 성격은 섞지 않는다.
QA 파일·실제 토스 응답·비밀정보는 프로덕션 번들에 포함하지 않는다.

[권장 실제 규모]
- 처음 완성 시 테스트·fixture·설정 전체 약 18~28개 파일
- 계산·저장·토스·기업행위·E2E처럼 변경 이유가 다른 영역만 분리
- 테스트 1개당 파일 1개 또는 화면 1개당 파일 1개 방식은 금지
- 버그 사례는 기존 도메인 테스트에 추가하고 복잡할 때만 별도 파일 생성
- 파일 개수 자체를 품질 목표로 사용하지 않는다.

[세 가지 QA 데이터]

1) 불변 fixture
- 손으로 독립 검산한 평단·원금·배당·세금·ROC·총수익 정답
- 실제 발생 버그의 최소 재현 데이터
- 토스 중복·정정·부분 실패·오류 응답
- 기업행위와 손상 백업 경계 사례
- 정의가 틀렸음이 확인되지 않는 한 기대값을 수정하지 않는다.

2) 버전 fixture
- schema-v1, schema-v2와 계산정책 버전을 원본 그대로 보존한다.
- 저장 포맷·토스 매핑·백업 포맷이 바뀌면 기존 파일을 덮지 않고 새 버전을 추가한다.
- 구버전 자료는 최신 버전으로 변환 후 원금·수량·누적배당·현금흐름을 보존해야 한다.

3) 생성 데이터
- 장기 거래·배당·환율·기업행위는 generator가 만든다.
- seed, 시작일, 기간, 종목 구성, 통화, 정책 버전을 기록한다.
- 같은 seed는 언제나 같은 이벤트와 요약 결과를 만들어야 한다.
- 대량 결과 파일을 쌓지 않고 실패 seed와 최소 축소 사례만 보존한다.

[처음 만들 최소 기준 세트]

- golden 계산 20~30개
- 대표 사용자 여정 10~15개
- 토스 성공·401·429·500·타임아웃·부분 성공·빈 응답·중복·정정 fixture
- 분할·병합·티커 변경·청산 fixture 각 최소 1개
- 과거 백업/스키마 최소 1개씩과 손상 백업 2개
- 1년·5년·10년·30년 generator 각 1개 프로필
- 데이터 0건·일반·큰 금액·음수·긴 이름·환율 실패 시각 상태
- 실제 수정한 버그부터 bugs/에 계속 누적

숫자는 시작 범위이며 테스트 개수 채우기가 목적이 아니다.
같은 의미의 사례를 중복해서 늘리지 않는다.

======================================================================
1-B. 기능 수정 시 QA 데이터를 유지하는 원칙
======================================================================

기능 하나를 수정할 때 모든 QA 데이터와 기대값을 바꾸지 않는다.

- UI 배치 변경: 금융 fixture는 그대로 두고 시각 기준만 의도 확인 후 갱신한다.
- 내부 리팩터링: 기존 기대값을 변경하지 않는다. 전후 결과 동일성이 목적이다.
- 새 기능: 관련 factory 옵션과 대표 시나리오만 추가한다.
- 버그 수정: 재현 fixture를 먼저 추가하고 수정 뒤 영구 회귀 자산으로 남긴다.
- 스키마 변경: 과거 fixture는 그대로 보존하고 새 버전과 migration 테스트를 추가한다.
- 배당/세금/환율 정책 변경: 적용일이 있는 정책 버전을 추가하고 과거 결과를 보존한다.
- 토스 응답 변경: 원본 전체를 저장하지 말고 비식별 최소 계약 fixture를 새 버전으로 추가한다.
- 기대값 변경: 구현 코드의 출력값을 복사하지 말고 독립 계산으로 승인한다.

많은 fixture를 동시에 고쳐야 한다면 먼저 factory 결합이나 도메인 경계 문제를 확인한다.
일반 기본값은 factory 한 곳에서 관리하되 golden·legacy·bugs fixture는 자동 변경하지 않는다.

======================================================================
1-C. 30년 호환성을 위한 영구 계약
======================================================================

다음은 UI보다 오래 유지할 DividendOS의 데이터 계약이다.

- 모든 영구 데이터에 schemaVersion을 둔다.
- securityId를 장기 식별자로 쓰고 표시 ticker 변경과 분리한다.
- 거래·배당·기업행위 원본 이벤트를 파생 합계와 분리한다.
- 실제·확정·예상 배당 상태와 전환 이력을 잃지 않는다.
- 금액·수량·통화·환율·반올림·날짜의 저장 규칙을 문서화한다.
- 토스 sourceId를 우선 보존하고 없을 때만 버전된 fingerprint 규칙을 사용한다.
- 동기화 cursor·요청 ID·정정/취소 관계를 저장해 재시도에도 멱등성을 보장한다.
- 마이그레이션은 순차 경로와 최신 결과를 검증하고 재실행해도 중복되지 않아야 한다.
- 백업에는 앱 버전·schemaVersion·생성일·무결성 정보를 포함한다.
- 과거 버전 비식별 백업을 회귀 자산으로 남긴다.
- Node·TypeScript·브라우저·DB 업그레이드 뒤에도 같은 입력의 금융 결과는 동일해야 한다.

[호환성 매트릭스]

정식 배포 전 최소 확인:
- 이전 운영 버전 저장 데이터 → 새 앱
- 이전 백업 포맷 → 새 앱 복원
- 구형 단일 문서 → 새 분할 저장 구조
- 토스 계약 fixture 구버전 → 최신 정규화 모델
- 오프라인 구버전 PWA → 온라인 신버전
- 휴대폰 생성 데이터 → PC 세션, 그리고 반대 방향

1-D. 장기 시뮬레이션 구성과 합격 조건
======================================================================

[필수 장기 사건]
- 주·월·분기 배당 혼합과 지급주기 변경
- 추가 매수·부분 매도·전량 매도·재진입
- 현금 수령과 재투자
- 배당 증가·감소·중단·특별배당
- 세금·수수료·ROC·환율 급변
- 분할·병합·티커 변경·합병·분사·청산
- 토스 지연·중복·정정·취소·부분 실패
- 오프라인 수정·동시 저장 충돌·백업 복원
- 예상→확정→실제 전환과 과거 배당 정정

[합격 불변식]
- 종목별 합계의 합 = 포트폴리오 합계 = 홈 표시 합계
- 거래·배당 원본으로 모든 파생값을 다시 계산할 수 있음
- 같은 토스 이벤트를 여러 번 받아도 한 번만 반영
- 정정·취소 후 원본 연결과 감사 이력이 유지
- 저장·복원·마이그레이션 뒤 수량·원금·누적배당·현금흐름 동일
- 기업행위 전후 경제적 가치와 원본 이력이 규칙대로 보존
- 통화 변환 반복이 원본 USD/KRW 값을 변형하지 않음
- NaN·Infinity·음수 불가 수량·미확인 환율의 0원 저장이 없음
- 응답 순서와 입력 순서가 달라도 같은 결과
- 같은 seed의 30년 요약 결과와 핵심 해시가 동일
- 실패 시 seed·연도·종목·이벤트까지 바로 축소·재현 가능

성능은 수천 명 접속 부하가 아니라 개인의 30년 데이터량을 기준으로 한다.
Galaxy S25 Ultra에서 홈·포트폴리오·종목 상세·백업 복원이 체감상 멈추지 않아야 한다.
현재 정상 버전의 측정값을 기준선으로 저장하고 이후 퇴행 여부를 판단한다.

======================================================================
1-E. 구축 순서와 실행 주기
======================================================================

[최초 구축]
1) 거래·배당·환율·기업행위 계산을 UI에서 분리한다.
2) schemaVersion, securityId, migration runner를 고정한다.
3) golden·legacy·토스·기업행위 fixture를 만든다.
4) factory와 고정 seed generator를 만든다.
5) 핵심 Playwright 흐름, 토스 중복, 백업 왕복을 자동화한다.
6) CI에서 Q0/Q1을 자동 실행하고 Q2/Q3는 위험도에 따라 실행한다.

[실행 주기]
- 코드 저장/PR: Q0
- 화면·일반 기능 완료: 관련 Q1
- 계산·저장·토스·권한·기업행위 변경: Q2
- 정식 큰 배포·스키마 메이저 변경: Q3와 30~35년 시뮬레이션
- 매월 또는 중요 데이터 누적 후: 백업 실복원 1회
- 분기 또는 주요 의존성 변경 전: 전체 회귀와 PWA 업데이트 확인
- 연 1회: 오래된 백업 복원, 토스 계약 변화, 복구 문서, 런타임 지원상태 점검

개인 앱이므로 변경이 없는 기간에 의미 없는 반복 실행은 하지 않는다.

======================================================================
1-F. 최종 실행 프로필 — 매번 전부 돌리지 않는다
======================================================================

테스트에는 @smoke, @core, @slow, @external 성격을 표시한다.

[FAST — 평소 수정]
- 타입·린트·변경 영역 단위 테스트
- 관련 smoke E2E
- 외부 실계정 호출 없음

[CORE — 기능 완료·PR·배포 후보]
- 금융 계산, 저장, 마이그레이션, 백업 왕복
- Chromium 모바일/데스크톱 핵심 E2E
- 비식별 토스 계약 fixture와 중복 판정
- 실패 시 trace와 화면만 보존

[FULL — 계산·스키마·토스 매핑·기업행위 변경]
- property-based·상태 순서 테스트
- 충돌·오프라인·RLS·서버 함수
- 1·5·10년 생성 데이터
- 핵심 화면 시각 회귀

[RELEASE — 큰 배포]
- 30~35년 생성 데이터
- 구버전 PWA→신버전
- 실제 Galaxy S25 Ultra
- 실제 토스 읽기 전용 대표 조회
- 백업 실복원과 롤백 확인

Playwright 재시도는 진단용 1회까지만 사용하고 첫 실패를 숨기지 않는다.
trace는 모든 성공 테스트에 남기지 않고 실패 또는 첫 재시도에만 남긴다.

======================================================================
1-G. 개인 앱에 맞춘 축소 확정안
======================================================================

- 상시 브라우저는 Chromium 모바일·데스크톱만 사용한다.
- Firefox·WebKit은 해당 브라우저 사용 계획이 생기거나 호환성 변경 때만 확인한다.
- 시각 회귀는 홈, 포트폴리오, 종목 상세, 입력창, 백업/복원, 토스 오류 상태에 한정한다.
- 모든 픽셀 차이를 차단하지 않고 금액 잘림·버튼 가림·그래프 오류를 우선한다.
- 코드 전체 100% 커버리지는 목표로 삼지 않는다.
- 계산·마이그레이션·중복·권한·기업행위처럼 손실 위험 영역의 미검증 분기를 우선한다.
- mutation testing, 대규모 부하, 다지역 장애복구, 24시간 관제는 도입하지 않는다.
- 실제 토스 호출은 매 QA마다 하지 않고 연동 변경·큰 배포·장애 의심 때만 최소 실행한다.
- 새 기능과 관련 없는 golden·legacy·bugs fixture는 수정하지 않는다.

======================================================================
1-H. 런타임·도구의 30년 교체 정책
======================================================================

Node 24와 TypeScript 7은 2026년의 개발 기준이지 30년 동안 고정할 버전이 아니다.
Node 24 LTS의 공식 지원 예정은 2028년 4월 말까지이므로 그 전에 후속 활성 LTS 전환을 검토한다.

- package.json engines, 버전 파일, lockfile로 현재 기준 버전을 고정한다.
- 활성 지원 중에는 보안·패치 버전을 정기 반영한다.
- Node 메이저는 지원 종료 전에 다음 활성 LTS로 이동한다.
- TypeScript·Vitest·Playwright 메이저 변경은 별도 브랜치에서 전체 회귀 후 반영한다.
- 런타임 교체 전후 동일 fixture의 수량·원금·배당·총수익 요약 해시를 비교한다.
- 업그레이드 때문에 금융 기대값을 일괄 갱신하지 않는다.
- 오래된 의존성을 억지로 고정하는 것보다 작은 주기 업그레이드를 우선한다.

- 운영 데이터 1개
- 자동 클라우드 백업 1개
- 사용자가 내려받은 암호화 또는 안전 보관 백업 1개
- 자동 백업은 최근 세대를 순환 보존하되 사용자 지정 중요 백업은 자동 삭제하지 않는다.
- 백업 생성 성공이 아니라 실제 복원 성공으로 검증한다.
- 복원 시험은 격리된 QA 저장소에서 하고 운영 데이터를 덮지 않는다.
- 토스 토큰·시크릿·세션·전체 계좌번호는 백업과 증빙에서 제외한다.

4. Playwright 핵심 사용자 흐름
======================================================================

1) 첫 실행 → 로그인 → 홈
2) 종목 생성 → 매수 → 추가 매수 → 부분 매도
3) 실제 배당 입력 → 세금 입력 → 월·연 합계 확인
4) 예상 배당 등록 → 확정 → 실제 전환
5) 거래·배당 수정 → 삭제 → 합계 복귀
6) 주·월·분기 배당 종목 혼합
7) 원화·달러 반복 전환
8) 그래프 기간·종목·상태 필터
9) 목표 생성·수정·달성·다음 목표
10) 토스 최초 동기화 → 재동기화 → 중복 0건
11) 토스 일부 실패 → 재시도 → 복구
12) 백업 → 초기 상태 → 복원 → 전체 비교
13) 오프라인 입력 → 온라인 복귀
14) 두 세션 동시 저장 → 충돌 처리
15) 로그아웃 → 재로그인 → 데이터 유지

각 테스트는 독립된 계정·저장소·데이터를 사용한다.
한 테스트 결과에 다음 테스트가 의존하지 않는다.

7. 장기 QA 데이터 규칙
======================================================================

30~35년 QA는 큰 배포 전 Q3에서만 실행한다.
작은 변경마다 전체 장기 QA를 반복하지 않는다.

포함할 시나리오:
- 배당주·고배당주 혼합
- 주·월·분기 지급주기
- 매수·추가 매수·부분 매도·전량 매도
- 재투자와 현금 수령
- 수수료·세금·ROC
- 환율 급변·실패
- 분할·병합·티커 변경·청산
- 실제·확정·예상 배당
- 토스 중복·정정·부분 실패
- 오프라인·동시 저장 충돌
- 백업·복원·구버전 마이그레이션

자동 생성 데이터는 고정 seed를 기록한다.
핵심 경계구간은 실제 UI에서 직접 입력·수정·삭제한다.
종료 후 QA 거래·배당·종목·토스 연결·클라우드 문서가 0건인지 확인한다.

- 앱 버전·커밋·schemaVersion
- 실패 화면 캡처

- 민감정보를 제거한 네트워크 오류
- 테스트 데이터 seed

규칙:
- 토스 토큰·시크릿·전체 계좌번호를 남기지 않는다.
- 재시도는 진단용 최대 1회다.
- 첫 실패 후 재시도 성공은 flaky로 기록한다.
- 대기시간만 늘려 통과시키지 않는다.
- 핵심 실패 테스트를 skip해 배포하지 않는다.

9. 배포 차단 기준
======================================================================

다음 중 하나라도 발생하면 배포하지 않는다.

- TypeScript·빌드·핵심 테스트 실패
- 평단·원금·수수료·세금·ROC·총수익 불일치
- 실제·확정·예상 배당 중복 합산
- 환율 실패를 0원으로 저장
- 백업 복원 결과 불일치
- 토스 시크릿·토큰 노출
- 토스 동일 거래·배당 중복 생성
- 토스 일부 실패를 전체 성공으로 표시
- 다른 사용자 데이터 접근 가능
- 클라우드 충돌의 무음 덮어쓰기
- 기업행위 뒤 과거 이력 손실
- Service Worker 혼합 버전
- 모바일 핵심 버튼 사용 불가
- 원인을 모르는 flaky 핵심 테스트
- QA 데이터가 운영 환경에 남음

11. 개인 앱 기준으로 하지 않을 과잉 QA
======================================================================

- 수십 종류 휴대폰 실기기 조합
- 수천 명 동시접속 부하 시험
- 24시간 유료 관제
- 모든 브라우저·운영체제 조합
- 의미 없는 전체 코드 100% 커버리지 숫자 맞추기
- 작은 문구 수정마다 30년 전체 QA
- 실제 토스·운영 데이터를 복제한 무분별한 테스트

핵심 결론:
DividendOS는 변경 위험에 따라 Q0~Q3를 선택한다. 평소에는 자동 타깃 QA가 반복 검사를 대신하고,
금융 계산·저장·토스·권한·기업행위 변경과 큰 배포에서만 강화 QA와 30~35년 최종 QA를 실행한다.
