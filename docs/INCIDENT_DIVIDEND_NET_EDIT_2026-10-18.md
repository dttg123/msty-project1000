# 기존 배당 실수령액 수정 오류 · 1.14

## 원인과 1.12/1.13 QA에서 놓친 이유

1.12에서는 `amountUSD:99, netAmountUSD:8.5`의 합계를 8.5로 고쳤지만, 수정 폼의 초기값과 개별 기록 formatter/주당 금액/검색은 여전히 `amountUSD`를 직접 읽었다. 수정 폼은 그 99를 세후 금액으로 받아 다시 `netAmountUSD`에 저장했다. 따라서 숫자를 건드리지 않거나 메모만 바꾸어도 실수령액이 8.5에서 99로 바뀔 수 있었다.

금액 엔진의 단위 검사에는 서로 다른 원시 금액과 실수령액 fixture가 있었지만, UI 검사는 주로 `amountUSD` 하나만 있는 새 입력 또는 두 값이 같은 기록을 사용했다. **합계 수정이 수정창·개별 표시까지 이어지는지, 기존 기록을 무변경 재저장해도 금융 의미가 유지되는지 확인하지 않은 것이 점검 누락이다.** 통과 건수가 많았다는 사실로 이 경로의 보존성을 확인했다고 볼 수 없다.

공개된 1.13 ZIP을 별도 서버에 그대로 풀어 재현했다. 화면 검사에서 수정창의 기대값 8.5에 실제값 99가 나왔고, 기록 목록도 99달러·주당 9.9달러를 보여 주었다. 두 재현 검사는 수정 전 실패했고 같은 경로를 수정 후 다시 검사한다.

다른 금액 경로도 대조했다. CSV는 이미 canonical net을 사용했고, ZIP은 원시 금융 필드를 보존했다. 홈/월별 합계와 그래프는 기존 reporting projection 및 실제 지급 필터를 거치고 있었다. 거래의 수수료·세금과 잔액 보정의 부호는 각 원래 필드 의미를 유지하며 이번 변경으로 일괄 정규화하지 않는다. 복원/저장 실패의 기존 rollback 회귀 검사도 다시 실행한다. 이는 모든 가능한 미래 오류가 없다는 보장은 아니다.

## 재발 방지와 범위

새 UI 회귀 검사는 순배당/원시 금액 충돌, 명시적 0, 작은 소수, 원화, 메모/날짜 변경, 재시작/ZIP 재독해, 표시/주당 금액/검색 일치, 실패 후 즉시 재시도, 실제 금액 수정, ROC 비율 수정, 통화 변경을 다룬다. 금융 formatter/search와 zero validation 경계도 기존 필수 finance suite에 추가했다. 새 UI 파일은 기존 CI의 전체 모바일·데스크톱 실행에 자동 포함된다.

재현/QA는 합성 자료와 분리된 저장소에서 수행한다. 배포는 사용자 기록을 일괄 변경하거나 누락된 실제 입금액을 추정하지 않는다. 과거 버전에서 이미 덮어쓴 값이 있다면 원본 거래내역 또는 덮어쓰기 전 백업과 대조해야 하며, 현재 코드만으로 원래 액수를 복구했다고 주장하지 않는다. Galaxy 실기기와 실제 계좌 확인은 배포 후 별도 상태로 남긴다.
